# AI 駆動グラフィックスプログラミング入門

## 1. AI 駆動開発（AI-DLC）とは

### 従来の開発スタイルとの違い

これまでのソフトウェア開発では、**人間がコードを書き、AI が補助する**というスタイルが主流でした。

```
従来スタイル:
  人間がコードを書く → AI にエラーを質問 → AI が修正案を出す → 人間が判断して取り込む
```

AI 駆動開発（AI-DLC: AI-Driven Development Life Cycle）は、この主従関係を逆転させます。

```
AI-DLC スタイル:
  AI が意図を読んでコードを生成 → 人間がレビュー・承認 → 人間が判断して修正・採用
```

AI-DLC では、**人間はコードを書く人から、判断・承認する人に変わります**。コードを速く書けるようになった分、人間の役割は「何を作るか」「なぜそう作るか」「本当に正しいか」を判断することにシフトします。

## 2. なぜ AI はコードを間違えるのか

### AI は「正しそうに見える」コードを生成する

AI はコードを書く際、過去の大量のコードパターンから確率的に次のトークンを選びます。これは「文法的に正しい」「よく見るパターンに似ている」という基準であり、「このプロジェクトで正しい」という基準ではありません。

**よくある間違いのパターン:**

#### パターン 1: 精度の問題

モバイル GPU ではメモリ帯域の節約と計算速度のために `half` 精度（16bit float）を使うのが標準ですが、AI は汎用的な `float`（32bit）を使いがちです。

```hlsl
// AI が生成しがちなコード（パフォーマンスバグ）
float2 direction = float2(-d.y, d.x);  // float: 32bit → モバイルで無駄

// 正しいコード
half2 direction = half2(-d.y, d.x);   // half: 16bit → モバイル向け最適
```

Mali Offline Compiler（Arm のモバイル GPU 静的解析ツール）でレジスタ使用量を比較すると、`float` 版の方がレジスタ数やサイクル数が増加することが確認できます。

#### パターン 2: アスペクト比の無視

UV 空間（0〜1 の正規化座標）でベクトル計算をするとき、画面の縦横比を考慮しないと視覚的に歪みが出ます。

```hlsl
// AI が生成しがちなコード（視覚的バグ）
half2 tangent = half2(-d.y, d.x);  // アスペクト比補正なし → 横長画面で楕円形になる

// 正しいコード（横長画面でも正円形のブラーになる）
half2 tangent = half2(-d.y, d.x) * half2(_ScreenParams.y * rcp(_ScreenParams.x), 1.0h);
```

UV 空間の x 方向と y 方向は「0 から 1」という同じスケールを持っていますが、実際の画面上の長さは異なります。例えば 1920×1080 の画面では、UV の x=1 は 1920px に相当し、UV の y=1 は 1080px です。ベクトル計算をピクセルベースで考えずに UV ベースのままにすると、円形であるべきエフェクトが楕円形になります。

#### パターン 3: ループの最適化漏れ

GPU シェーダーでは、ループのイテレーション数がコンパイル時に確定している場合、`UNITY_UNROLL` を使って展開することで分岐コストを削減できます。

```hlsl
// AI が生成しがちなコード（動的ループ / パフォーマンスバグ）
int sample_count = 8;  // 実行時変数 → コンパイル時定数ではない
for (int n = 0; n < sample_count; n++)
{
    blur_color += SAMPLE_TEXTURE2D(...);
}

// 正しいコード（定数 → UNITY_UNROLL で展開可能）
#define BLUR_SAMPLING_COUNT 6
UNITY_UNROLL
for (int n = 0; n < BLUR_SAMPLING_COUNT; n++)
{
    blur_color += SAMPLE_TEXTURE2D(...);
}
```

#### パターン 4: 合成式のズレ

加算サンプリングした色を平均化する際、サンプル数（合計何回加算したか）で割る必要があります。AI が「定数で割ればいい」と判断すると、実際のサンプル数とズレてビジュアルデグレが発生します。

```hlsl
// AI が生成しがちなコード（ビジュアルデグレ）
blur_color *= 1.0h / 8.0h;  // 定数 8 で割る → 実際のサンプル数と異なる可能性

// 正しいコード（実際のサンプル数を正確に使う）
const int sample_count = 1 + _SamplingCount + (_UseInverse ? _InverseSamplingCount : 0);
blur_color *= rcp(sample_count);  // 実際の合計サンプル数で割る
```

## 3. なぜコードレビューが不可欠か

### AI が生成したコードは「動く」が「正しい」とは限らない

上記のバグはいずれも、**コンパイルが通り、ゲームが動き続ける**ものです。クラッシュしないため、一見すると気づけません。しかし：

- **精度バグ**: ローエンドモバイルデバイスでフレームレートが下がる。ユーザー体験に直結するが、開発機（ハイエンド PC）では気づかない。
- **アスペクト比バグ**: 横長画面（= モバイルの標準）で視覚的に歪む。開発中に縦画面でしか確認しないと見逃す。
- **合成式バグ**: 微妙に明るさが変わる。ビジュアルリグレッションテストがなければ検出できない。

### 3 つの防衛線

| 防衛線 | 検出できるもの | 検出できないもの |
|---|---|---|
| コードレビュー（目視） | 明らかなロジックミス、精度の使い分け | 視覚的な差分、モバイル実機特有の問題 |
| ビジュアルリグレッションテスト | ピクセル単位の変化（合成式のズレ等） | パフォーマンス劣化 |
| モバイル GPU 静的解析（Mali OC 等） | レジスタ数増加、サイクル数増加 | ビジュアルの正しさ |

**3 つをすべて使うことで、AI 生成コードの品質を担保できます。**

## 4. この演習でやること

### Part 2: RotationBlur 新規実装

AI が意図的に 2 種類のバグを含む「回転ブラーエフェクト」のシェーダーコードを生成します。あなたの役割は：

1. **視覚的バグ**: 横長画面でブラーが楕円形になることを確認 → アスペクト比補正を追加して修正
2. **パフォーマンスバグ**: Mali Offline Compiler でレジスタ数・サイクル数を確認 → `half` 精度に修正

### Part 3: DirectionalBlur 高品質化改修

AI が既存の `DirectionalBlur` に対して「より高品質なサンプリング」と称してバグを含む改修コードを生成します。あなたの役割は：

1. **パフォーマンスバグ**: Mali Offline Compiler でサイクル数の劣化を確認 → サンプリング数を適正に戻す
2. **ビジュアルデグレ**: ビジュアルリグレッションテストで差分を検出 → 合成式を修正

どちらの演習も、「AI が生成したコードをそのまま使うと問題が起きる」を体験し、**レビュー・測定・テストの重要性**を実感することがゴールです。

## 参考: UV 空間とアスペクト比補正の直感的な理解

```
画面: 1920 × 1080 px
UV空間: x ∈ [0, 1] → 1920px に対応
         y ∈ [0, 1] → 1080px に対応

UV の中心 (0.5, 0.5) から右端 (1.0, 0.5) へのベクトル:
  UV ベクトル: (0.5, 0)
  ピクセルベクトル: (960, 0) px

UV の中心から上端 (0.5, 0) へのベクトル:
  UV ベクトル: (0, -0.5)
  ピクセルベクトル: (0, -540) px

→ 「UV の長さが等しい」≠「画面上の長さが等しい」
   UV ベクトル (0.5, 0) と (0, 0.5) は UV 空間で同じ長さだが、
   ピクセルでは 960px vs 540px = 1.78 倍の差がある

アスペクト比補正:
  _ScreenParams.y / _ScreenParams.x = 1080 / 1920 ≈ 0.5625
  
  UV x 方向のベクトルに 0.5625 を掛けることで、
  x 方向の「UV 単位あたりのピクセル数」の大きさを y 方向に揃える
```
